tachograph: system guide

A flight recorder for coding agents. One daemon per machine records agent actions into a single SQLite WAL event log (events.sqlite), serving compact status and claim verification to supervising agents in ~180 tokens and duration-first traces to ui.perfetto.dev.

Part 1 — Fundamentals

1Why a flight recorder for agents

Coding agents fail in ways traditional logging cannot capture. When a supervisor drives four worker agents across a codebase, three distinct failure modes emerge:

  • Context exhaustion: Raw agent logs are enormous. A single four-worker refactoring run generates 97 MB of JSON transcripts. Ingesting those transcripts into a supervisor agent exhausts its context window in two turns.
  • Invisible parallel work: Agents execute parallel tool calls and subagent trees. Text logs flatten overlapping async calls into sequential output, obscuring which tool blocked, which command ran concurrently, and where wall-clock time was lost.
  • Post-mortem blindspots: When an agent enters an infinite retry loop, silently hangs on a compilation command, or claims tests pass without running them, developers have no deterministic way to inspect host system counters (CPU, memory, child process trees) alongside agent actions.

tachograph solves this by recording every turn, tool call, command, wait, and counter into a structured SQLite WAL timeline. A supervisor inspects running workers via tacho status, tacho watch, and tacho report --diff-claims using under 200 tokens. A developer opens tacho trace in ui.perfetto.dev to inspect duration slices, state bands, and step-function counters down to the nanosecond.

Part 2 — Storage & Lifecycle

2Architecture & SQLite WAL single source of truth

tachograph operates as a single resident process (tacho daemon) started on demand by any client that finds no socket. It uses no async runtime: all paths run on plain OS threads and non-blocking IPC sockets.

Every event recorded by the system is persisted into a single SQLite WAL table ($TACHO_HOME/events.sqlite). There are no separate in-memory event ring buffers: SQLite WAL is the sole durable source of truth. Every trace written by tacho trace is rendered directly from SQLite rows through a streaming zero-allocation projector, and supervisor state is deterministically folded from the exact same event stream.

Write path vs Read path execution

To ensure high throughput and resilience, tachograph decouples write and read operations across four distinct paths:

Part 3 — Data Model

3Track hierarchy & virtual lanes

Perfetto models events along tracks. Slice tracks in Perfetto represent execution as a strict stack: a child slice must begin after and end before its parent. Overlapping sibling slices on a single track corrupt the visualization.

Coding agents routinely violate stack nesting: LLMs fire multiple parallel tool calls within a single turn, subagents run concurrently, and tools take variable time to return. tachograph resolves this with a deterministic LaneAllocator and projecting every event as a true duration slice, TYPE_STATE transition, or step-function counter — with zero zero-duration instant clutter.

Track hierarchy structure

├── agents

Counter semantics and step-function deduplication

Perfetto counter tracks are rendered as step-functions: each sample retains its value until the next sample on that track. To prevent log bloat without losing precision, tachograph applies strict event-driven and deduplicated recording rules:

  • Event-driven counters: Slices and telemetry such as active_builds, active_tests, files_edited, commits, tokens_in, tokens_out, tokens_cached, and cost emit strictly on event occurrence or value change.
  • Polled host and process counters: Machine load (machine/load1, machine/cpu_busy, machine/mem_used, machine/disk:*) and per-agent process tree metrics (agent:<id>/run:<n>/proc_count, cpu, rss) are polled every 2 seconds from /proc and cgroup v2. Consecutive identical values are deduplicated in the sampler: a sample is written to SQLite WAL only when its value actually changes.
Part 5 — Anomaly Detection

5Anomaly & stall detectors

The appender evaluates stall detectors after every ingested event and on a periodic tick. When a detector fires, it records a Stall event, transitions agent:<id>/state to Stalled, opens a duration slice on agent:<id>/stalls until the agent recovers or exits, and optionally invokes the configured on_stall shell hook.

DetectorThreshold TriggerDiagnostic Meaning
SILENT 300 seconds without an event while not in a Wait Agent wedged or unresponsive. CPU-aware: checks agent:<id>/run:<n>/cpu deltas; suppresses while process tree burns CPU (e.g. 25-minute cargo clippy or test suite).
LOOP Same tool input digest repeated 4 times consecutively Agent is stuck in an automated retry loop or failing tool call
SPIN 8 turns without a FileEdited or BUILD/TEST/COMMIT Agent is wandering across read/list commands without making progress
BURN > 200,000 output tokens consumed in 10 minutes (or per-task budget) Runaway generation loop, prompt inflation, or task budget exhaustion
FAILING Same build/test command fails 3 times consecutively Agent repeatedly running broken tests without adjusting implementation
OFF_BRIEF FileEdited occurs on path outside task's declared scope Agent hallucinated modifications to files outside declared --paths
CLAIM Run completes (exit 0) after edits without a passing test Agent prematurely claims task completion without verifying that tests pass

Ground-truth claim verification: tacho report <agent> --diff-claims

Coding agents often declare success in conversation while leaving broken code or failing tests. The --diff-claims flag cross-references the agent's assertions against ground truth recorded in the SQLite event log and git worktree:

  • File edits: Verifies whether any FileEdited events were recorded during the run.
  • Test verification: Asserts that at least one command classified as TEST completed with exit code 0 after the final file edit.
  • Commit & push tracking: Checks whether commits or pushes were executed and whether the working tree is clean.
# Compare agent claims against verifiable execution events
tacho report worker-2 --diff-claims

# Example output when an agent claims completion without testing:
=== Claim Verification: worker-2 ===

Commits Succeeded:    0

Claim Stall Flags:    CLAIM

Part 6 — Integration

6Ingestion modes

tachograph requires no changes to agent binaries. Five ingestion modes capture events across different environments:

1. Provider hooks (Claude Code, Gemini CLI, Jetski)

Hooks execute in < 5 ms. They convert provider lifecycle events into NDJSON and send them to api.sock. Hooks exit 0 silently if the daemon is unavailable.

# Automatically configure hooks in provider settings
tacho install claude
tacho install gemini
tacho install jetski

2. Process wrapping: tacho run -- <cmd>

Executes the target command in a child process (placed into a dedicated systemd / cgroup v2 scope when available), tees stdout, parses stream-json events, and tracks child processes, CPU, and RSS over the process tree.

# Wrap any agent CLI: stdout is passed through byte-for-byte
tacho run -- claude --output-format stream-json
tacho run -- codex exec --json "implement feature x"

3. Live transcript tailing: tacho tail

Watches on-disk Claude Code .jsonl transcripts via inotify, persisting per-file (dev, inode, offset) checkpoints atomically in $TACHO_HOME/tail-offsets.json and handling file rotation or truncation automatically.

# Continuously watch and ingest transcripts under ~/.claude/projects
tacho tail ~/.claude/projects

# Ingest new lines once and exit
tacho tail ~/.claude/projects --once --agent worker-1

4. OpenTelemetry: OTLP HTTP receiver

Accepts standard OTLP/HTTP protobuf or JSON on 127.0.0.1:4318 for agents instrumented with OpenTelemetry.

5. Shell scripting: tacho emit

# Declare a supervisor task with declared paths, assigned agent, base commit, and budgets
tacho emit task auth-refactor \
  --paths crates/core/src/auth.rs,crates/core/src/token.rs \
  --agent worker-1 \
  --base-commit 7c3b2f1 \
  --token-budget 100000 \
  --cost-budget 500000 \
  --brief-file brief.md

# Emit custom spans and task state transitions
tacho emit span begin custom:migration "phase-1" --arg schema=v2
tacho emit state auth-refactor InProgress --because "worker-1 started"
tacho emit span end custom:migration

Declared task paths bound the scope for the OFF_BRIEF detector. Per-task token and cost budgets set thresholds for the BURN detector. Subsequent runs assigned to the same task are automatically connected with Perfetto flow arrows (task_run_flow:<slug>) to preserve execution lineage across retries.

Part 7 — Host Corroboration

7Process tree tracking (cgroup v2 + /proc) & Perfetto traced

Coding agents spawn deep trees of short-lived child processes (cargo check, rustc, cargo-nextest, git). tachograph tracks both kernel cgroup v2 accounting and /proc process hierarchies:

  • Process-tree slot tracks (procs/slot 0..k): Child processes spawned under an agent run are tracked across sampling intervals and rendered as duration slices on deterministic slot tracks (e.g. rustc (pid 4120)), with shell noise filtered out.
  • Unified cgroup v2 + /proc metrics: When a run executes inside a dedicated cgroup v2 leaf, the sampler reads cgroup.procs, cpu.stat, and memory.current alongside /proc/<pid> traversal, reporting the maximum of /proc RSS and cgroup memory.current on agent:<id>/run:<n>/rss.
  • Perfetto traced merge: Dual-clock synchronization (CLOCK_REALTIME + CLOCK_BOOTTIME) merges kernel scheduler slices and CPU frequency from traced when running tacho trace --system.

Fault-tolerant process reaping and storage degradation

In production agent fleets, workers may crash, get killed by OOM killers, or exhaust host storage. tachograph handles these conditions automatically:

  • Dead worker reaping: During each /proc sampling cycle, the daemon inspects the PID tree of active runs. If a tracked PID terminates or enters a zombie state (ESRCH or process state 'Z'), the daemon automatically marks the run complete and closes all open child tool slices with abandoned = true.
  • Graceful storage degradation: If the host disk runs out of space (ENOSPC) or the filesystem becomes read-only, SQLite WAL writes degrade safely without crashing the daemon or blocking agent hook callers.
Part 8 — Analytics

8PerfettoSQL queries

tachograph ships 10 production queries in queries/. Every query is implemented in standard SQL and PerfettoSQL pipe syntax with 100% row equivalence.

-- Execute shipped query against running daemon
tacho query agents-now
tacho query contention
tacho query system-during-builds
tacho query verified-trees

Git tree verification: verified-trees

Every command of class BUILD, TEST, LINT, COMMIT, PUSH, or REBASE captures the underlying Git tree hash (git rev-parse HEAD^{tree}). The verified-trees query tracks which trees have passing builds and tests for CI reuse and merge trains:

-- queries/verified-trees.sql
SELECT
  c.git_tree,
  COUNT(DISTINCT c.agent) AS verifying_agents,
  MIN(c.ts_ns) AS first_verified_ts,
  MAX(c.ts_ns) AS last_verified_ts
FROM command_slices c
WHERE c.command_class IN ('BUILD', 'TEST')
  AND c.exit_code = 0
  AND c.git_tree IS NOT NULL
GROUP BY c.git_tree;

Interval intersection of agent builds and system RSS

Here is queries/system-during-builds.pipe.sql using PerfettoSQL's native interval intersection:

INCLUDE PERFETTO MODULE intervals.intersect;

-- Intersect agent build slices with kernel scheduler slices
CREATE PERFETTO TABLE _agent_sched_intersection AS
SELECT * FROM _interval_intersect!(
  (agent_builds, s_agent),
  (system_sched_slices, s_cpu)
);

SELECT
  agent,
  slice_name AS command,
  dur / 1e6 AS wall_ms,
  cpu_time_ns / 1e6 AS cpu_ms,
  peak_rss_bytes / (1024 * 1024) AS peak_rss_mb
FROM _agent_sched_intersection
ORDER BY wall_ms DESC;
Part 9 — Privacy

9Content firewall & default-on secret scrubber

tachograph separates structural telemetry from raw content and runs a default-on regex/shape scrubber on everything that leaves the process or enters the log:

  • Always Dropped (Content Firewall): Model prose, user prompts, tool stdout/stderr, file diff contents, raw environment variables, and message bodies are never stored. They are represented solely by 8-byte BLAKE3 digests and byte lengths.
  • Path Relativization: Absolute file paths inside the workspace are converted to relative paths (src/main.rs). Paths outside the workspace are masked to <outside>/....
  • Default-On Secret Scrubber (scrub = true by default; opt-out via scrub = false or TACHO_SCRUB=0): By default, command-line arguments (argv), custom args, finding titles, status outputs, issues, emails, and log tails are scrubbed before leaving the process or persisting to disk:
    • Sensitive flags: --token, --password, -p, --api-key, --secret replaced with <redacted>.
    • Sensitive headers & URL userinfo: Authorization: Bearer <redacted>, https://user:<redacted>@host.
    • Key shapes: AWS (AKIA...), GCP (ya29...), GitHub (ghp_..., github_pat_...), Anthropic (sk-ant-...), OpenAI (sk-...), Slack (xoxb-...), JWT triples, and PEM blocks.
    • High-entropy hex/base64 runs ≥ 32 characters (with 40-character hexadecimal Git commit SHAs explicitly preserved).
