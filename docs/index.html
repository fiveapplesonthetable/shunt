tachograph: system guide

A flight recorder for coding agents. One daemon per machine records agent actions into a single SQLite WAL event log, serving compact status to supervising agents in ~180 tokens and microsecond traces to ui.perfetto.dev.

Part 1 — Fundamentals

1Why a flight recorder for agents

Coding agents fail in ways traditional logging cannot capture. When a supervisor drives four worker agents across a codebase, three distinct failure modes emerge:

  • Context exhaustion: Raw agent logs are enormous. A single four-worker refactoring run generates 97 MB of JSON transcripts. Ingesting those transcripts into a supervisor agent exhausts its context window in two turns.
  • Invisible parallel work: Agents execute parallel tool calls and subagent trees. Text logs flatten overlapping async calls into sequential output, obscuring which tool blocked, which command ran concurrently, and where wall-clock time was lost.
  • Post-mortem blindspots: When an agent enters an infinite retry loop or silently hangs on a compilation command, developers have no deterministic way to inspect host system counters (CPU, memory, load) alongside agent actions.

tachograph solves this by recording every turn, tool call, command, wait, and counter into a structured binary timeline. A supervisor inspects running workers via tacho status and tacho watch using under 200 tokens. A developer opens tacho trace in ui.perfetto.dev to inspect microscopic timings down to the nanosecond.

Part 2 — Storage & Lifecycle

2Architecture & SQLite WAL single source of truth

tachograph operates as a single resident process (tacho daemon) started on demand by any client that finds no socket. It uses no async runtime: all paths run on plain OS threads and non-blocking IPC sockets.

Every event recorded by the system is persisted into a single SQLite WAL table ($TACHO_HOME/events.sqlite). There are no secondary in-memory event rings: SQLite WAL is the sole durable source of truth. Every trace written by tacho trace is rendered directly from SQLite rows through a streaming zero-allocation encoder.

Write path vs Read path execution

To ensure high throughput and resilience, tachograph decouples write and read operations across four distinct paths:

PathMechanismLatencyDisk AccessFailure Mode

Part 3 — Data Model

3Track hierarchy & virtual lanes

Perfetto models events along tracks. Slice tracks in Perfetto represent execution as a strict stack: a child slice must begin after and end before its parent. Overlapping sibling slices on a single track corrupt the visualization.

Coding agents routinely violate stack nesting: LLMs fire multiple parallel tool calls within a single turn, subagents run concurrently, and tools take variable time to return. tachograph resolves this with a deterministic LaneAllocator.

Track hierarchy structure

tacho                                   # Root track: host identity, version
├── machine                             # Counters: load1, cpu_busy, mem_used, disk
├── daemon                              # Lifecycle, snapshots, clock steps, errors
│   └── counters                        # events, trace_us, queue_depth
├── agents
│   └── agent:<id>                      # Long-lived worker (provider, model, cwd)
│       ├── state                       # TYPE_STATE: Idle, Thinking, Tool, Waiting, Stalled, Exited
│       └── run:<n>                     # Provider session
│           ├── turns                   # Nested: Turn > ToolCall | Build | Test | Read
│           ├── lane:1 .. lane:k        # Virtual lanes for concurrent tool executions
│           ├── waits                   # Blocked intervals (user prompt, subagent message)
│           ├── tokens_in / out / cost  # Token accounting and cumulative cost counters
│           └── cpu / rss               # Process-tree resource counters from /proc
├── tasks
│   └── task:<slug>                     # Orchestrator work item with declared paths
│       ├── state                       # TYPE_STATE: Queued, Active, Review, Done
│       └── review                      # Review findings and code inspection spans
└── custom
    └── custom:<name>                   # Spans and counters emitted via `tacho emit`
Part 4 — Protocol & Schema

4Event catalogue & TrackEvent extensions

tachograph extends Perfetto's standard perfetto.protos.TrackEvent in the unallocated range 4000–4099. Every trace begins with an ExtensionDescriptor packet embedding the compiled FileDescriptorSet of tacho.proto, allowing Trace Processor to decode all typed fields into the args table automatically.

Extension FieldNumberTypeDescription
seq4000uint64Global monotonically increasing event sequence number
cause_seq4001uint64Sequence number of the causal antecedent event
agent4002stringAgent identifier, enabling SQL filters without track joins
command4003CommandArgv, command class, exit code, working directory
tool_call4004ToolCallTool name, input digest (Blake3), call ID
turn_ended4005TurnEndedTurn duration, tokens in, tokens out, tokens cached
file_access4006FileAccessPath relative to cwd, access kind (Read, Search, List)
file_edited4007FileEditedPath, lines added, lines removed, patch digest
wait4008WaitWait reason, timeout, target sender ID
stall4009StallDetector kind (LOOP, SPIN, SILENT, BURN), evidence

Counter semantics and step-function deduplication

Perfetto counter tracks are rendered as step-functions: each sample retains its value until the next sample on that track. To prevent log bloat without losing precision, tachograph applies strict event-driven and deduplicated recording rules:

  • Event-driven counters: Slices and telemetry such as active_builds, active_tests, tokens_in, tokens_out, tokens_cached, and cost_micros emit strictly on event occurrence or value change.
  • Polled host and process counters: Machine load (machine/load1, machine/cpu_busy, machine/mem_used, machine/disk:*) and per-agent process tree metrics (agent:<id>/run:<n>/cpu, agent:<id>/run:<n>/rss) are polled every 2 seconds from /proc. Consecutive identical values are deduplicated in the sampler: a sample is written to SQLite WAL only when its value actually changes.
Part 5 — Anomaly Detection

5Anomaly & stall detectors

The appender evaluates stall detectors after every ingested event and on a 1-second periodic tick. When a detector fires, it emits a StallDetected instant and transitions the agent track to Stalled.

DetectorThreshold TriggerDiagnostic Meaning
LOOP Same tool input digest repeated 4 times consecutively Agent is stuck in an automated retry loop or failing tool call
SPIN 8 turns without a FileEdited or BUILD/TEST/COMMIT Agent is wandering across read/list commands without making progress
SILENT 300 seconds without an event while not in a Wait Agent process wedged, network hang, or dead without exit hook
BURN > 200,000 output tokens consumed in a 10-minute window Runaway generation loop or prompt regression consuming budget
FAILING Same build/test command fails 3 times consecutively Agent repeatedly running broken tests without adjusting implementation
OFF_BRIEF FileEdited occurs on path outside task's declared scope Agent hallucinated modifications to unrelated files in workspace
Part 6 — Integration

6Ingestion modes

tachograph requires no changes to agent binaries. Four ingestion modes capture events across different environments:

1. Provider hooks (Claude Code, Gemini CLI, Jetski)

Hooks execute in < 5 ms. They convert provider lifecycle events into NDJSON and send them to api.sock. Hooks exit 0 silently if the daemon is unavailable.

# Automatically configure hooks in provider settings
tacho install claude
tacho install gemini
tacho install jetski

2. Process wrapping: tacho run -- <cmd>

Executes the target command in a child process, tees stdout, parses stream-json events, and tracks CPU/RSS over the process tree using its known PID.

# Wrap any agent CLI: stdout is passed through byte-for-byte
tacho run -- claude --output-format stream-json
tacho run -- codex exec --json "implement feature x"

3. OpenTelemetry: OTLP HTTP receiver

Accepts standard OTLP/HTTP protobuf or JSON on 127.0.0.1:4318 for agents instrumented with OpenTelemetry.

4. Shell scripting: tacho emit

# Declare a supervisor task with bounded paths
tacho emit task auth-refactor --paths crates/core/src/auth.rs --brief-file brief.md

# Emit custom spans and progress instants
tacho emit span begin custom:migration "phase-1" --arg schema=v2
tacho emit instant custom:migration "checkpoint" --arg status=ok
tacho emit span end custom:migration
Part 7 — Host Corroboration

7System tracing with Perfetto traced

When investigating performance issues or heavy builds, tachograph correlates agent slices with kernel activity via Perfetto's system daemon (traced).

tachograph synchronizes clocks by capturing paired readings of CLOCK_REALTIME and CLOCK_BOOTTIME at the start of the trace. When writing a snapshot with tacho trace --system, tachograph clones the active tacho-system ring buffer and merges the packets.

Part 8 — Analytics

8PerfettoSQL queries

tachograph ships 9 production queries in queries/. Every query is implemented in standard SQL and PerfettoSQL pipe syntax with 100% row equivalence.

-- Execute shipped query against running daemon
tacho query agents-now
tacho query contention
tacho query system-during-builds

Interval intersection of agent builds and system RSS

Here is queries/system-during-builds.pipe.sql using PerfettoSQL's native interval intersection:

INCLUDE PERFETTO MODULE intervals.intersect;

-- Intersect agent build slices with kernel scheduler slices
CREATE PERFETTO TABLE _agent_sched_intersection AS
SELECT * FROM _interval_intersect!(
  (agent_builds, s_agent),
  (system_sched_slices, s_cpu)
);

SELECT
  agent,
  slice_name AS command,
  dur / 1e6 AS wall_ms,
  cpu_time_ns / 1e6 AS cpu_ms,
  peak_rss_bytes / (1024 * 1024) AS peak_rss_mb
FROM _agent_sched_intersection
ORDER BY wall_ms DESC;
Part 9 — Privacy

9Privacy firewall & scrubbing

tachograph enforces a strict privacy firewall in the appender thread before persistence. If a secret is intercepted, it is redacted before writing to SQLite or memory.

  • Never Stored: Model prose, user prompts, tool stdout/stderr, file diff contents, raw environment variables, and message bodies are dropped immediately. They are represented solely by Blake3 8-byte digests and byte lengths.
  • Always Scrubbed: Command-line arguments (argv), custom args, and task titles pass through regex and shape scrubbers.
  • Redaction Patterns:
    • Sensitive flags: --token, --password, -p, --api-key, --secret replaced with <redacted>.
    • Sensitive headers: Authorization: Bearer <redacted>.
    • Key shapes: AWS (AKIA...), GCP (ya29...), GitHub (ghp_..., github_pat_...), Anthropic (sk-ant-...), OpenAI (sk-...), Slack (xoxb-...), JWT triples, and PEM blocks.
    • High-entropy hex/base64 runs ≥ 32 characters.
    • Preserved: 40-character hexadecimal Git commit SHAs are explicitly exempted and preserved.
  • Path Relativization: Absolute file paths inside the workspace are converted to relative paths (src/main.rs). Paths outside the workspace are masked to <outside>/....
